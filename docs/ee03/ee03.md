# Module 3 (EE03): Dev Tooling & Version Control

## 1. Which Version We Built On

We had two versions of the site, one by [`Joshua (jandoh08)`](https://github.com/jandoh08/the-corner-loaf) and one by [`Samuel-Attu`](https://github.com/Samuel-Attu/the-corner-loaf). We compared them against four core engineering questions:

1. **Does it build and run without errors?**
2. **How many issues from Modules 1 and 2 are still open?**
3. **Could a stranger find their way around the folders?**
4. **Which is cheaper to bring the other's best ideas into?**

### Decision: We built on `jandoh08/the-corner-loaf`

| Question                             | `jandoh08`                                                                                                                                                                                                | `Samuel-Attu`                                                                                                                                                                          |
| :----------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Builds & runs**                    | Yes, clean execution with no console errors.                                                                                                                                                              | Yes, clean execution with no console errors.                                                                                                                                           |
| **Open issues**                      | Zero open issues from Module 1; automated accessibility checks across axe-devtools, WAVE, and Lighthouse identified zero errors.                                                                          | Zero open issues from Module 1; axe-devtools flagged 1 contrast issue, while WAVE and Lighthouse reported clean passes.                                                                |
| **Navigability by a stranger**       | **Clear and modular:** `index.html` at the repository root, CSS split by concern, JS split into native ES modules, and separate documentation folders per module (`docs/ee01`, `docs/ee02`, `docs/ee03`). | **Monolithic & confusing:** `ee02/` held only documentation while EE02 code fixes lived under `ee01/`; styles and logic lived in a 1,289-line `styles.css` and a 955-line `script.js`. |
| **Cost to absorb the other's ideas** | **Low:** Modular root structure allows two developers to work on different sections simultaneously without colliding.                                                                                     | **High:** Changes require touching large monolithic files, creating frequent merge conflicts.                                                                                          |

Additional engineering considerations favoring `jandoh08`:

- **Clean accessibility baseline:** Zero WCAG 2.2 AA contrast failures, Accra-timezone live status polling, Windows High Contrast Mode (`forced-colors: active`) support, and a functional `<noscript>` fallback.
- **Lower integration cost:** Native ES modules allowed Vite to drop in without reorganizing code.

### Why this structure helps a team:

- **Parallel development:** Developers can work on different CSS and JS files without colliding on git diffs.
- **Single sources of truth:** Menu items and opening hours change in `js/data.js` only; design colors change in `css/tokens.css` only.
- **Asset predictability:** Static assets in `public/` are served at root and copied verbatim to `dist/`, avoiding Vite bundle hashing where not wanted.

## 3. Team Conventions & Git Workflow

We adhere to standard Gitflow conventions throughout the project lifecycle:

### Branching Strategy

- **`main`**: Production-ready code only. Pushes trigger automated deployment to GitHub Pages.
- **`develop`**: Integration branch for ongoing work. Finished work is merged here first before a release to `main`.
- **`feature/<name>`** (e.g. `feature/project-documentation`): For new features, enhancements, or documentation. Created off `develop` and merged back into `develop` via pull request.
- **`bugfix/<name>`**: For fixing issues identified in development code. Branches off and merges into `develop`.
- **`hotfix/<name>`**: Urgent fixes to production. Merges into both `main` and `develop`.

### Commits & Daily Workflow

1. Pull latest `develop`.
2. Create your branch off `develop` (`feature/<task>` or `bugfix/<task>`).
3. Make atomic, single-purpose commits using **Conventional Commits**:
   - Format: `type(scope): subject`
   - Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
   - Examples: `feat(order): add pickup date validation`, `docs(ee03): combine tooling documentation`.
4. Pull `develop` into your branch locally and resolve any merge conflicts before pushing.
5. Push your branch to GitHub and open a Pull Request targeting `develop`.

### Pull Request & Review Process

- **PR Template (`.github/pull_request_template.md`):** Every PR must answer four core questions:
  1. **What does this PR do?**
  2. **Why was this change made?**
  3. **How was this tested?**
  4. **Are there any breaking changes?**
- **Automated Quality Gate:** All CI checks (`lint`, `format:check`, `build`) must pass.
- **Review Etiquette:** Authors conduct a self-review and link issues. Reviewers label comments (`nit`, `question`, `suggestion`, `issue`) and clearly distinguish `blocking` items from `optional` feedback.

## 4. Configuration Reference

| File or Setting                       | What It Does                                                                                                                                                                  | Why It Matters for a Team                                                                                                            |
| :------------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------- |
| **`package.json`**                    | Defines project metadata, npm scripts (`dev`, `build`, `lint`, `format`), dependencies, and `lint-staged` triggers.                                                           | Guarantees every collaborator runs the exact same development scripts and has identical tools installed with a single `npm install`. |
| **`package-lock.json`**               | Pins the transitive dependency tree to exact versions.                                                                                                                        | Ensures `npm ci` installs identically on every machine and CI runner, eliminating "works on my machine" version drifts.              |
| **`.nvmrc`**                          | Pins Node.js version (Node 26).                                                                                                                                               | Ensures both developers and CI execute under identical Node runtimes.                                                                |
| **`vite.config.js`**                  | Configures Vite dev server and sets the base path to `/the-corner-loaf/`.                                                                                                     | Eliminates `file://` CORS issues during development and ensures assets resolve correctly when hosted on GitHub Pages subpaths.       |
| **`.gitignore`**                      | Ignores `node_modules/`, `dist/`, logs, `.DS_Store`, and `.env*`.                                                                                                             | Prevents build artifacts and local secrets from polluting git history or causing large diff conflicts.                               |
| **`.prettierrc.json`**                | Enforces code formatting: semicolons, single quotes, 2-space indentation, and ES5 trailing commas.                                                                            | Removes subjective formatting debates from PR reviews; code style is automatically normalized.                                       |
| **`.prettierignore`**                 | Prevents Prettier from altering generated/machine files like `dist/` and `package-lock.json`.                                                                                 | Avoids noisy diffs and keeps CI format checks focused solely on source code.                                                         |
| **`eslint.config.js`**                | Flat ESLint config checking browser JS for bugs, undefined variables, and unused vars, with Node environment enabled for `*.config.js`. Paired with `eslint-config-prettier`. | Catches logic errors and dead code before runtime without clashing with Prettier rules.                                              |
| **`stylelint.config.js`**             | Checks CSS stylesheets against `stylelint-config-standard`, flagging syntax errors and deprecated properties while disabling noisy stylistic/BEM clashes.                     | Safeguards 10 raw modular stylesheets against real CSS bugs and obsolete properties while allowing custom class naming schemes.      |
| **Husky `pre-commit`**                | Executes `npx lint-staged` prior to creating any commit.                                                                                                                      | Catches linting errors or unformatted files locally in milliseconds before code leaves the developer's laptop.                       |
| **`lint-staged`**                     | Runs ESLint and Prettier on staged JS, Stylelint and Prettier on staged CSS, and Prettier on staged HTML/JSON/Markdown/YAML.                                                  | By only checking staged files, commits stay fast while automatically auto-fixing format issues.                                      |
| **Husky `commit-msg` + `commitlint`** | Validates commit messages against Conventional Commits via `commitlint.config.js`.                                                                                            | Enforces clear, searchable, and machine-parsable commit histories across all team members.                                           |
| **`.github/workflows/ci.yml`**        | Automated GitHub Actions workflow on PRs and pushes to `develop` and `main` that runs `npm ci`, `npm run lint`, `npm run format:check`, and `npm run build`.                  | Provides an unskippable server-side gate ensuring failing or unformatted code cannot merge even if local hooks were skipped.         |
| **`.github/workflows/deploy.yml`**    | Builds and deploys the site to GitHub Pages on merges to `main`.                                                                                                              | Automates continuous deployment while ensuring non-main branches never deploy prematurely to production.                             |

## 5. Workflow Improvements Added

During Module 3, two permanent workflow improvements were implemented to protect team velocity and production reliability:

### 1. `commitlint` + Standardized PR Template

- **What was added:** `commitlint.config.js`, `.husky/commit-msg`, and `.github/pull_request_template.md`.
- **Problem it solves:** Prevents vague, unhelpful commits (e.g., `"updates"`, `"fix"`) and incomplete pull requests lacking test steps or context.
- **Who it protects:** Protects collaborators during code review, future maintainers investigating git history, and Marcus's bakery business by ensuring changes are traceable.
- **Why keep it permanently:** Enforces professional engineering rigor automatically without requiring manual policing from the reviewer.

### 2. GitHub Branch Protection Rules

Branch protection rules are configured on both `main` and `develop`:

- **Require a pull request before merging:** Prevents direct pushes to shared branches.
- **Require status checks to pass (`check`):** Merges are blocked if CI (`npm run lint`, `npm run format:check`, `npm run build`) fails.
- **Require branches to be up to date before merging:** Ensures feature branches integrate current `develop` code before merging.

## 6. Known Limitations

- **Local bypassability:** Local Git hooks can technically be bypassed with `git commit --no-verify`. CI is the true unskippable quality gate.
- **Repository settings persistence:** Branch protection rules live in GitHub repository settings rather than version-controlled files, requiring manual setup if the repository is mirrored or recreated.
- **Accessibility automation limits:** Automated CI checks cover syntax, formatting, and build viability, but cannot evaluate subjective WCAG criteria. Manual keyboard navigation and screen-reader testing from Module 2 remain mandatory before releasing changes.
