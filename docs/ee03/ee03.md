## 3. Conventions followed

### Branches

- **`main`**: Production-ready code; pushes trigger deployment to GitHub Pages.
- **`develop`**: Integration branch for current work; merges into `main` for releases.
- **`feature/<name>`** / **`bugfix/<name>`**: Short-lived branches created off `develop` and merged back via pull request.

### Commits & daily workflow

1. Pull latest `develop`.
2. Branch off `develop` (`feature/<task>` or `bugfix/<task>`).
3. Commit small changes using **Conventional Commits** (`type(scope): subject`, e.g. `feat(order): add pickup date selection`).
4. Pull `develop` into your branch to resolve any conflicts locally.
5. Push branch and open a Pull Request targeting `develop`.

### Pull requests

- **Title**: Follows `type(scope): subject` (used as the squashed commit title on merge).
- **Checks**: Must pass CI (lint, formatting, and build) before merge.
- **Description**: Answers four standard questions:
  1. What does this do?
  2. Why is it needed?
  3. How was it tested?
  4. Are there any breaking changes?
- **Review**: Self-review first, link the related issue, and request review before merging.

## 4. Configuration reference

| File or setting                         | What it does                                                                                                                                                                                                                                     | Why it matters for a team                                                                                                                                                                                                                                                                                                    |
| :-------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `package.json`                          | Lists every package the project depends on (Vite, ESLint, Prettier, Husky and so on) with the versions it accepts, and defines the npm scripts used to run, build, lint and format the project.                                                  | A new developer clones the repo and runs `npm install` to get the same toolchain, with no list of tools to install by hand. A tool added by one person reaches everyone on the next `npm install`. The scripts mean both developers and CI run the same commands.                                                            |
| `package-lock.json`                     | Records the exact version of every installed package, including the packages those packages depend on. `npm ci` installs exactly what it lists.                                                                                                  | `package.json` allows a range of versions, so two installs on different days can differ. The lockfile makes both laptops and CI use identical versions, so a check that passes for one person does not fail for the other.                                                                                                   |
| `.nvmrc`                                | Pins the Node major version.                                                                                                                                                                                                                     | CI and both laptops run the same Node, so a difference in runtime cannot cause a failure that only one person sees.                                                                                                                                                                                                          |
| `vite.config.js`                        | Sets the base path `/the-corner-loaf/` for the build.                                                                                                                                                                                            | The site is published under a sub-path on GitHub Pages. Without the base path the built files would point to the wrong place and the live site would load without its styles, scripts or images.                                                                                                                             |
| `.gitignore`                            | Tells Git which files never to track: `node_modules` (reinstalled from `package.json`), `dist` (generated by the build and rebuilt by CI), `.env` files (local settings and secrets), and operating-system and editor files such as `.DS_Store`. | The repository holds only source files. Generated folders would cause huge diffs and merge conflicts, and a secret committed once stays in the Git history even after it is deleted. It also meets the review rule "no unnecessary files" before a reviewer sees the pull request.                                           |
| `.prettierrc`                           | Sets the formatting rules: semicolons, single quotes, 2-space indentation and ES5 trailing commas.                                                                                                                                               | Formatting is decided once, by the tool. Diffs then show real changes instead of style differences, and nobody spends review comments on spacing or quotes.                                                                                                                                                                  |
| `.prettierignore`                       | Lists files Prettier must skip: generated or machine-written files such as `dist` and `package-lock.json`.                                                                                                                                       | Nobody edits those files by hand, because tools regenerate them. Formatting them would add noisy diffs, and `format:check` in CI could fail on files that no developer can meaningfully fix.                                                                                                                                 |
| `eslint.config.js`                      | Sets the rules ESLint uses to find likely bugs: unused variables, undefined names, and other mistakes in the recommended rule set. It is configured for browser code written as ES modules, and turns off any rule that clashes with Prettier.   | Prettier handles style and ESLint handles correctness. The site has no compile step, so a typo in a variable name or an import would only show up when that code runs in the browser. ESLint finds it before then. A shared rule set also turns "I think this is wrong" in a review into a result both developers agreed on. |
| Husky `pre-commit` hook                 | Runs lint-staged before every commit.                                                                                                                                                                                                            | Mistakes are caught in seconds, before they reach a pull request.                                                                                                                                                                                                                                                            |
| lint-staged                             | Runs ESLint and Prettier on staged files only.                                                                                                                                                                                                   | Checking only the files in the commit keeps the hook fast, so nobody is tempted to skip it.                                                                                                                                                                                                                                  |
| Husky `commit-msg` hook with commitlint | Rejects commit messages that do not follow Conventional Commits.                                                                                                                                                                                 | The convention is enforced by the tool, not by memory, so the history on `develop` stays readable.                                                                                                                                                                                                                           |
| `.github/workflows/ci.yml`              | On every pull request, runs install, lint, format check and build.                                                                                                                                                                               | This is the check that cannot be skipped. Local hooks can be bypassed with `--no-verify`, but CI runs on GitHub, and with branch protection it can block a merge.                                                                                                                                                            |
| `.github/workflows/deploy.yml`          | On merge to `main`, builds the site and publishes `dist/`.                                                                                                                                                                                       | Only `main` publishes, so work on `develop` and on feature branches can never go live by accident.                                                                                                                                                                                                                           |

## 5. Improvement to the development workflow: Branch Protection

We implemented **GitHub Branch Protection Rules** on both `main` and `develop`.

### Rules configured

- **Require a pull request before merging**: Disables direct pushes to `main` and `develop`.
- **Require status checks to pass (`check`)**: Blocks merging if CI (lint, format check, or build) fails.
- **Require branches to be up to date before merging**: Ensures PR branches integrate the latest `develop` before merge.

### What problem does it solve?

Agreed-upon team conventions (peer reviews, running tests, resolving merge conflicts locally) are easily forgotten or bypassed during rushed deadlines. Branch protection turns these voluntary guidelines into hard repository guardrails: broken code cannot be accidentally pushed straight to production or integration branches.

### Who does it protect?

- **The Developers**: Protects teammates from pulling broken code or dealing with unexpected merge conflicts caused by unreviewed commits.
- **The Reviewer**: Guarantees that code arriving for review is already linted, properly formatted, building cleanly, and up-to-date with `develop`.
- **The User/Business**: Prevents broken builds, faulty asset paths, or untested code from deploying live to the customer-facing GitHub Pages site.

### Why is it worth adding permanently?

Local Git hooks alone are not enough because any developer can bypass them with `git commit --no-verify`. Branch protection provides an unskippable safety net at the remote level with zero ongoing maintenance cost, ensuring consistent code quality across current and future contributors.

## 6. Known limitations

- Git hooks live on each developer's machine and can be bypassed with `git commit --no-verify`. CI is the check that cannot be skipped.
- Branch protection is a GitHub setting, not code, so it does not travel with a clone or fork and has to be set again on a new repository.
- Automated checks cover formatting, code errors and the build. They do not check accessibility, so the manual keyboard and screen-reader checks from Module 2 are still needed.
