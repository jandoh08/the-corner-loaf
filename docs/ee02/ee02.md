## 1. What went wrong, and why

One of Marcus's regulars is blind. He tried to check the week's bakes with his screen reader and heard "item, item, item" with no way to tell what belonged to what.

In my EE01 build the cause was structural. The weekly menu was a table with no row headers, so a price or a day was read out with no item name attached. Samuel's audit confirmed it as finding 1, rated Critical. The same pattern, meaning that only works if you can see it, also appeared in the cedi symbol, the FAQ icons and the form errors. This round fixes the cause in each place and not only the symptom Marcus heard about.

## 2. My audit of Samuel's site

I tested with WAVE, Lighthouse, keyboard only, browser zoom and very large text at 320px, and NVDA. His site scored well on automated checks and was readable by screen reader from start to finish. The failures that mattered came from enlarged text, which scanners do not catch.

| Rank   | Finding                                                                                                                                      | Criterion                                  | Severity       |
| :----- | :------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------- | :------------- |
| 1      | Prices overlap item names when text is enlarged on a phone                                                                                   | 1.4.4, 1.4.10 (AA)                         | Significant    |
| 2      | Day links land with the heading hidden under the sticky header                                                                               | Closest is 2.4.11; otherwise best practice | Moderate       |

I ranked by whether a problem blocks the main job of the page, which is reading what is baked and what it costs. The full reasoning, reproduction steps and screenshots are in the audit.

## 4. Fixes for Samuel's findings

| #   | Samuel's finding (severity)                                                  | What I did                  |
| :-- | :--------------------------------------------------------------------------- | :-------------------------- |
| 1   | Table had no row headers (Critical)                                          | Removed the table. See 4.1. |
| 2   | Text cut off at very large font size (Significant)                           | See 4.3.                    |
| 3   | Weak focus rings and borderless buttons in high contrast (Significant)       | See 4.2.                    |
| 4   | Cedi symbol skipped, repeated image descriptions (Moderate)                  | See 4.1.                    |
| 5   | FAQ not in the heading list, "plus" read aloud, no skip link (Moderate)      | See 4.1 and 4.4.            |
| 6   | Focus stayed on Submit after an error, order type reset the item (Moderate)  | See 4.4.                    |
| 7   | No autofill, no required marker, plain-text contact details (Recommendation) | See 4.1.                    |

### 4.1 Semantic structure (WCAG 1.3.1, 1.1.1, 1.3.5, 3.3.2)

- **Schedule (finding 1).** Samuel's suggested fix was to add row headers and a caption. I removed the table instead. Each bake is now an `<article>` with its name as an `<h3>`, inside a list, so a screen reader announces a list with a count and each item carries its own name. This is the fix for the "noise" Marcus's regular described.
- **Day picker.** The days, plus an "All" option for the whole week, are radio buttons in a `<fieldset>` with a `<legend>`, so the group has one tab stop and the arrow keys move between days. The selected day appears as a heading after the radios, so a screen reader user can jump past all of them. A visually hidden status line announces the new day and the number of bakes.
- **Prices (finding 4).** Narrator dropped the cedi symbol and read "GH 28". On the cards the visible "GH₵ 28" is hidden from assistive technology and a hidden "28 Ghana cedis" is read instead. The Item dropdown cannot contain hidden text, so it shows the price in words, for example "Banana Bread (15 cedis per slice)".
- **Images (finding 4).** Each of the six bakes has its own photo and its own description. Four items used to share "A selection of freshly baked treats".
- **FAQ (finding 5).** Native disclosure elements give the expanded state for free. The "plus" came from the CSS icon, which now has empty alternative text (`content: "+" / ""`), so it is no longer read aloud. Samuel also noted that the H key skipped the questions. I kept them as disclosure controls and not headings, as a deliberate trade-off. They are controls inside one section, so seven more headings would lengthen the heading list for everyone who is not looking for the FAQ. The "Common Questions" heading takes a user to the section and Tab reaches every question.
- **Open status and hours.** The status is shown once, in the bakes section, and has a full-sentence version for screen readers ("The bakery is closed right now and opens tomorrow at 7am"). The opening hours use plain words ("Monday to Friday", "7am to 5pm") because "Mon – Fri" and the dash were read out as abbreviations and punctuation.
- **Forms (finding 7).** The name fields have `autocomplete="name"`. I used a plain "All fields are required." line in place of asterisks, because it works for everyone without needing an explanation. The phone and email fields Samuel mentioned no longer exist, since enquiries go to WhatsApp. The WhatsApp number, phone number, email address and map address are now links.

### 4.2 Colour contrast and high contrast (WCAG 1.4.3, 1.4.11, 2.4.7)

- **Focus rings (finding 3).** Fields and buttons show a 3px outline with a 2px offset. The ring colour `#8b4513` against white measures 7.10:1, and `#4a2c0a` against a light background is about 12:1, both well above the 3:1 needed for focus indicators.
- **Submit buttons in forced colours (finding 3).** `border: 0` became a 2px transparent border, with an explicit `ButtonText` border under `forced-colors: active`. Forced colours removes backgrounds, so without a border the buttons were bare text.
- **Order type toggle.** Testing in forced-colours mode showed that the "Today's order" and "Pre-order" options lost their borders and their selected state, which relied on a shadow. They now have real borders, the selected option uses the system `Highlight` colours, and a check mark marks it so colour is not the only signal.

### 4.3 Text resizing and reflow (WCAG 1.4.4, 1.4.10)

- **Product cards (finding 2).** `overflow: hidden` is removed, the price and the name wrap, the text column can shrink, and the card stacks image-above-text on narrow screens.
- **What a real phone showed.** Testing at the largest text size and 200% zoom on a phone found more than the 320px test did. My spacing is in `rem`, so padding doubled along with the text and squeezed the forms. Form padding now follows the screen width, the quantity stepper no longer overflows, the opening hours wrap, and the small-screen breakpoints are in `rem`, so they also trigger when text is enlarged.
- **Fields sized to their content.** In the order form, each field is as wide as the longest value it will hold: a short field for the time, a narrow one for the quantity, and wider ones for the item and the name. A field's width hints at the answer it expects, and every field wraps to full width on a phone. The cost is a less uniform look than equal-width fields.

### 4.4 Keyboard and focus (WCAG 2.4.1, 2.4.3, 3.3.1)

- **Skip link (finding 5).** A "Skip to main content" link is the first focusable element.
- **Contact errors (finding 6).** An invalid submit moves focus to the field that needs fixing, marks it with `aria-invalid`, links it to the message with `aria-describedby`, and announces the error through a status region. On the order form the browser's own validation moves focus to the first invalid field.
- **Order form (finding 6).** The order type now comes before the item, the chosen item is kept when it still applies to the new type, and the help text is a live region so the change is announced.
- **Anchors.** `scroll-padding-top` keeps section headings clear of the sticky header, the failure I found on Samuel's site.

## 5. Additional improvement: respecting reduced motion

**Who the audit did not consider.** Samuel's audit covered screen readers, keyboard, contrast and text size. It did not cover people with vestibular disorders or motion sensitivity, for whom smooth scrolling across the page can cause dizziness and nausea.

**What I did.** In `base.css`, a `prefers-reduced-motion: reduce` block turns off smooth scrolling and shortens animations and transitions to near zero:

```css
@media (prefers-reduced-motion: reduce) {
  html {
    scroll-behavior: auto;
  }

  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

**Why it matters here.** The skip link and every navigation link scroll the page, and customers move between sections all the time. People who have asked their device for less motion get instant jumps. The setting is a user preference set on the device, so honouring it costs Marcus nothing. This relates to WCAG 2.3.3 (Level AAA), beyond the AA target.

**Other changes in this round** that were not asked for in the audit:

- The quantity stepper has 44px buttons for people with hand tremors. The quantity is limited to 10, which is stated in the label and in the FAQ, and over-limit values are corrected or blocked with a message.
- A `<noscript>` message replaces the forms and the day picker with the weekly schedule and the phone and WhatsApp links when JavaScript is off.

## 6. Known limitations

- **The page cannot confirm an order was sent.** Orders and messages open WhatsApp with the text filled in, and the customer must press send there. The page says so, and offers the number as a fallback.
- **Needs JavaScript.** The schedule, day picker and forms are built by script. With it off, a notice with phone and WhatsApp links replaces them.
- **Not tested:** VoiceOver (iPhone and Mac Safari) and TalkBack (Android) were not tested.

## 7. How I checked

- **Automated:** WAVE, Lighthouse accessibility audit and the W3C HTML validator, with errors fixed and re-run.
- **Keyboard:** the whole page by Tab, Shift+Tab, Enter, Space and arrow keys, including the day picker, FAQ and both forms.
- **Screen reader:** NVDA.
- **Text size and zoom:** very large text at 320px in Chrome, and the largest text size with 200% zoom on a real phone.
- **High contrast:** forced-colours emulation in Chrome DevTools.
- **Reduced motion:** emulated in DevTools, and the section links jump instead of scrolling.
