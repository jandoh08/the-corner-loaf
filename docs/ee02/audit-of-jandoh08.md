# Accessibility audit: The Corner Loaf site by jandoh08

- Site audited: https://jandoh08.github.io/the-corner-loaf/
- Audited by: Samuel Attu
- Standard: WCAG 2.2, level AA

## How I tested
- Automated tools: Chrome DevTools Accessibility & Lighthouse inspection, DOM/ARIA rule checks, and WebAIM Contrast Checker across all foreground/background colour pairs.
- Keyboard: Microsoft Edge / Chrome on Windows; did not touch the mouse and tested the full page journey from top to bottom using `Tab`, `Shift + Tab`, `Enter`, `Space`, and `Arrow` keys (placing an order, scrolling the weekly bakes table, opening and closing all four FAQ items, and submitting the contact form).
- Zoom, text size and reflow: Tested browser page zoom at `400%`, DevTools responsive viewport at `320px` CSS width, browser appearance font size set to **Very Large**, and Windows High Contrast (Forced Colors) themes (`Left Alt + Left Shift + PrtScn`).
- Screen reader: Windows Narrator (`Win + Ctrl + Enter`); tested heading navigation (`H`), table navigation (`T` and `Ctrl + Alt + Arrow` keys), button activation, and live form validation/submission announcements.
- Pages and journeys covered: Single-page bakery storefront (`index.html`), tested during both evening (`Closed · Opens tomorrow at 7am`) and live daytime (`Open now · Closes 5pm`) hours, covering: (1) checking today's available bakes and prices, (2) checking the weekly baking schedule in *This Week's Bakes*, (3) placing both a *Today's Order* and a *Pre-Order*, (4) reading the *Pre-Order FAQ*, and (5) sending an inquiry via *Send Us a Message*.

## Summary
Marcus, the rebuilt site already has a strong visual and structural foundation: the colour contrast is clear and easy to read in bright light, the main sections are neatly organised, and order confirmations and phone number prompts are read out properly when someone submits the form. However, a few hidden barriers still shut out the exact customers you want to serve. Most importantly, a blind customer using a screen reader to check *This Week's Bakes* hears prices and baking days with only row numbers (`"row 2 of 7"`) instead of the bread names, and hears `"GH 28"` because the cedi symbol (`₵`) is skipped aloud. In addition, customers with low vision who set their browser font size to *Very Large* have most of the product text cut off on screen, and anyone navigating with a keyboard instead of a mouse loses sight of which form box or submit button they are currently on. Fixing these issues is straightforward and will make checking bakes and placing orders effortless for every regular.

### 1. Screen reader users cannot tell which bread a price or baking day belongs to in "This Week's Bakes"
- **Principle, criterion and severity:** Perceivable; 1.3.1 Info and Relationships (Level A) — **Critical**.
- **Who it affects and how:** Blind screen reader users (like Marcus's regular customer). Sighted customers scan left across a row to see that `GH₵ 35` and `Tuesday & Friday` belong to `Sourdough Loaf`, but without programmatic row headers, a blind customer hears a disconnected list of numbers and days and has to give up and message Marcus on WhatsApp instead.
- **What was found:** In *This Week's Bakes* (`<table class="menu-table">` in `index.html` line 62 and `renderMenuTable()` in `js/script.js` lines 132–150), jumping to the table (`T`) and reading down the *Price* or *Available* column (`Ctrl + Alt + Down Arrow`) announced only `"GH 28, row 2 of 7"`, `"gh 20, row 3 of 7"` (`M1`). Every cell in the row—including `product.name` in column 1—is created with `document.createElement("td")` instead of `<th scope="row">`, and the table has no `<caption>`.
- **What to fix:** In `renderMenuTable()` (`js/script.js`), create the first cell in each row (`index === 0`) as `<th scope="row">` and the remaining three cells as `<td>`, and add `<caption class="sr-only">Weekly baking schedule and prices</caption>` inside `<table class="menu-table">`.

### 2. Product text is cut off when the browser font size is set to "Very Large"
- **Principle, criterion and severity:** Perceivable; 1.4.4 Resize Text (Level AA) and 1.4.10 Reflow (Level AA) — **Significant**.
- **Who it affects and how:** Older customers and people with low vision (like Elias or Ama's customer) who rely on browser-level *Very Large* font settings rather than only full-page zoom. When text is clipped at the card edges, they cannot read the descriptions or prices of today's fresh bakes.
- **What was found:** At `400%` page zoom alone, nothing overlaps, but enabling Chrome/Edge **Very Large** font size (`M9`) cuts off text across the *Available Today* product cards (`css/styles.css` lines 384–425). `.product-card` sets `display: flex; flex-direction: row; overflow: hidden;`, `.product-image` uses a fixed `rem` width (`var(--width-3xs)` = `5rem`, which scales up with the root font size), and `.product-price` forces `white-space: nowrap;`.
- **What to fix:** Allow `.product-card` and `.product-header` to wrap (`flex-wrap: wrap`), remove `overflow: hidden` from text containers (applying `border-radius` directly to `.product-image`), and constrain `.product-image` with `min(5rem, 30%)` (or stack cards vertically on narrow viewports) so enlarged text wraps freely.

### 3. Keyboard users cannot see which form field or submit button has focus, and submit buttons lose their borders in Windows High Contrast mode
- **Principle, criterion and severity:** Operable; 2.4.7 Focus Visible (Level AA), and Perceivable; 1.4.11 Non-text Contrast (Level AA) — **Significant**.
- **Who it affects and how:** Sighted keyboard-only users (people with motor impairments, hand tremors, or a broken arm in a cast) and low-vision users in Windows High Contrast mode. Without a visible focus ring or button border across the 10 form controls, filling out an order or submitting a message becomes guesswork.
- **What was found:** Tabbing through the page (`M5`) showed a clear focus ring on the table and FAQ buttons, but focus disappeared or became nearly invisible on all 8 `.form-field` inputs and both `.form-submit` buttons (*Submit Order* and *Send Message*). In `css/styles.css` (lines 285–307), `.form-field:focus` sets `outline: none;` with only a **1.46 : 1** border colour change (`#767676` to `#8b4513`) and a faint `0.12` shadow, while `.form-submit` has no `:focus-visible` rule and sets `border: 0;`, making both submit buttons look completely borderless in Windows High Contrast mode (`M10`).
- **What to fix:** Remove `outline: none` on `.form-field:focus`, add `outline: 2px solid var(--secondary-color); outline-offset: 0.25rem;` to `.form-field:focus-visible` and `.form-submit:focus-visible`, and replace `border: 0;` on `.form-submit` with `border: var(--border-width-thick) solid transparent;`.

### 4. Screen readers skip the Ghana Cedi symbol (`GH₵`) and announce generic/mismatched stock image descriptions
- **Principle, criterion and severity:** Perceivable; 1.1.1 Non-text Content (Level A) and 1.3.1 Info and Relationships (Level A) — **Moderate**.
- **Who it affects and how:** Blind screen reader users hear `"GH 28"` instead of `"28 Ghana cedis"` on every product and price, and hear a repetitive, inaccurate stock description (`"A selection of freshly baked treats"`) before reaching each item's actual heading.
- **What was found:** Windows Narrator (`M2`) skips the Unicode Cedi symbol (`₵`, `U+20B5`) output by `formatPrice()` (`js/script.js` lines 59–62) across *Available Today*, the *Item* dropdown, and *This Week's Bakes*. In addition, four distinct items (*Chin Chin*, *Butter Croissants*, *Banana Bread*, and *Meat Pies* in `js/script.js` lines 21–55) reuse `images/bofrot.jpg` with the generic `alt="A selection of freshly baked treats"`.
- **What to fix:** Provide an accessible spoken label for prices (e.g., `<span aria-hidden="true">GH₵ 28</span><span class="sr-only">28 Ghana cedis</span>` in cards/table cells, and `"28 Ghana cedis"` or `GHS` in `<option>` text), and set `alt=""` on decorative/stock product thumbnails where the adjacent `<h3>` and `<p>` already describe the item.

### 5. Screen reader heading navigation (`H` key) skips all four FAQ questions, FAQ buttons read out `"plus"`, and there is no "Skip to main content" link
- **Principle, criterion and severity:** Perceivable; 1.3.1 Info and Relationships (Level A), Operable; 2.4.1 Bypass Blocks (Level A) and 2.4.6 Headings and Labels (Level AA), and Robust; 4.1.2 Name, Role, Value (Level A) — **Moderate**.
- **Who it affects and how:** Screen reader users who skim pages using the `H` key miss all four FAQ questions and hear redundant punctuation (`"plus"`) when tabbing to each question; keyboard-only users must tab through all 6 order form controls on every visit to reach the schedule or FAQ.
- **What was found:** Pressing `H` in Windows Narrator (`M3`) jumped straight from `<h2>Pre-Order FAQ</h2>` to `<h2>About The Corner Loaf</h2>` because the `<button class="faq-trigger">` elements (`index.html` lines 77–102) are not wrapped in `<h3>` headings. Tabbing to each FAQ button (`M4`) announced `"plus"` at the end of every question because `.faq-trigger::after { content: "+"; }` (`css/styles.css` line 240) is not hidden from assistive technology. Finally, `<body>` has no skip link at the top of the page.
- **What to fix:** Wrap each `<button class="faq-trigger">` inside an `<h3>` heading, move the `+` symbol into `<span class="faq-icon" aria-hidden="true">+</span>` (or use CSS `content: "+" / "";`), and add `<a href="#main-content" class="skip-link">Skip to main content</a>` as the first element in `<body>`.

### 6. Contact form errors leave keyboard focus on the Submit button, and changing "Order Type" silently resets the selected item above it
- **Principle, criterion and severity:** Understandable; 3.3.1 Error Identification (Level A), and Robust; 4.1.2 Name, Role, Value (Level A) — **Moderate**.
- **Who it affects and how:** Keyboard and screen reader users must `Shift + Tab` backwards to find and fix the email field after an error, and customers ordering during daytime hours lose their selected bakery item without warning if they change the order type at the bottom of the form.
- **What was found:** Submitting an email without a domain dot (`abc@invalid`) in *Send Us a Message* (`js/script.js` lines 234–256) announces `"Please enter a valid email address"` via `role="status"` (`M8`), but leaves keyboard focus on **Send Message** and never sets `aria-invalid="true"` or `aria-describedby="contact-status"` on `#contact-email`. In *Place an Order* (`index.html` lines 21–54), `#order-type` is placed below `#order-item-select`; live daytime testing (`Open now · Closes 5pm`) confirmed that selecting `Sourdough Loaf (GH₵ 35)` and then switching `#order-type` between *Today's Order* and *Pre-Order* silently resets `#order-item-select` back to `"Select an item"` and updates `#order-form-help` without `aria-live`.
- **What to fix:** In `initContactForm()` (`js/script.js`), set `emailInput.setAttribute("aria-invalid", "true")`, link `aria-describedby="contact-status"`, and call `emailInput.focus()` on error. In `#order-form` (`index.html`), move **Type** (`#order-type`) above **Item** (`#order-item-select`) and add `aria-live="polite"` to `#order-form-help`.

### 7. Personal form fields lack autofill (`autocomplete`), required fields have no visual marker, and WhatsApp/email contact details are plain text
- **Principle, criterion and severity:** Perceivable; 1.3.5 Identify Input Purpose (Level AA), and Understandable; 3.3.2 Labels or Instructions (Level A) — **Recommendation / Minor**.
- **Who it affects and how:** People with motor impairments, dyslexia, or memory loss (like Elias) who rely on browser autofill to avoid typing errors across two forms, sighted users checking which fields are mandatory, and mobile users trying to tap the WhatsApp number or email address.
- **What was found:** In `index.html`, `#order-name` (line 40), `#order-contact` (line 45), `#contact-name` (line 119), and `#contact-email` (line 123) have no `autocomplete` attributes; required fields have `required` in HTML but no visual `*` or `(required)` text on their `<label>` elements; and `WhatsApp: 0551 000 000` and `Email: thecornerloaf@email.com` (`index.html` line 111) are plain text without `<a>` links.
- **What to fix:** Add `autocomplete="name"`, `autocomplete="tel"`, and `autocomplete="email"` to the personal inputs; add a visual required marker (`<span aria-hidden="true">*</span>`) to required labels; and wrap the contact details in `<a href="https://wa.me/233551000000">` and `<a href="mailto:thecornerloaf@email.com">` links.

## What works well
- **Colour contrast across the entire palette (WCAG 1.4.3 & 1.4.11):** Tested with the WebAIM Contrast Checker. Every text element passes Level AA (`4.5:1`), and almost all pass Level AAA (`7.0:1`), including the hero title (`#ffffff` on `#8b4513`, **7.10 : 1**), hero subtitle (`#f5deb3` on `#8b4513`, **5.40 : 1**), body text (`#222222` on `#f9f9f9`, **15.11 : 1**), section headings (`#4a2c0a` on `#f9f9f9` / `#f5deb3`, **12.05 : 1** / **9.65 : 1**), muted text (`#444444` on `#ffffff` / `#f9f9f9`, **9.74 : 1** / **9.25 : 1**), error messages (`#b3261e` on `#f9f9f9`, **6.21 : 1**), and unfocused input borders (`#767676` on `#f9f9f9`, **4.31 : 1**).
- **Page language, title, landmarks, and main heading order (WCAG 3.1.1, 2.4.2, 1.3.1, 2.4.6):** `<html lang="en">` and a descriptive `<title>` are set; `<header>`, `<main>`, `<section>`, and `<footer>` landmarks are used properly; and headings step cleanly from `<h1>` to `<h2>` to `<h3>` without skipping levels.
- **320px responsive reflow and isolated table scrolling (WCAG 1.4.10, Manual test M11):** At `320px` CSS width, the page reflows into a single vertical column with no page-level horizontal scrolling. Only the *This Week's Bakes* data table scrolls horizontally inside its `.table-wrapper` (`tabindex="0"`), which is an allowed two-dimensional exception under WCAG 1.4.10.
- **Order confirmation and contact status live regions (Manual tests M6 & M8):** Submitting *Place an Order* (tested for both *Today's Order* and *Pre-Order*) with the keyboard appends the order to `#order-list` (`aria-live="polite"`), which Windows Narrator announces clearly and immediately without reading the `|` separator symbols aloud; likewise, `#contact-status` (`role="status"`) immediately announces contact form status and error messages aloud.
- **Phone number format validation (Manual test M7):** Entering an invalid phone number (`123`) in `#order-contact` and pressing `Enter` displays a clear browser validation popup and reads out the required format (`0551 000 000`) from the `title` attribute via Windows Narrator.
- **FAQ accordion keyboard activation and focus ring (Manual tests M4 & M5):** The FAQ questions are built with real `<button type="button">` elements (`aria-expanded`, `aria-controls`, and `hidden` panels). Keyboard testing confirmed a clear focus ring on the table wrapper and FAQ buttons, and pressing `Enter` or `Space` toggles the answers reliably while announcing `"expanded"` / `"collapsed"`.
- **Tap target sizes (WCAG 2.5.8):** All inputs (`44px` height), buttons (`42.7px` height), and FAQ triggers (`25.6px` height) exceed the `24×24 CSS pixel` minimum target size.

## Not tested, and limits of this audit
- **Mobile screen readers on physical phones:** Tested with Windows Narrator on a Windows desktop browser; did not test with TalkBack on Android or VoiceOver on iOS or any other mobile screen reader.
- **Speech-input / voice-control software:** Did not test with Dragon NaturallySpeaking or Windows Voice Access or any other speech-input tool.
